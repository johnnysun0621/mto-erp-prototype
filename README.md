# 勝芳進銷存 Demo（MTO ERP 需求訪談原型）

單檔 HTML/CSS/JS 的可互動原型，模擬紙業（Make-to-Order／訂單驅動生產）的進銷存核心流程：報價 → 訂單 → 供應決策 → 裁切／採購 → 出貨 → 發票 → 單據追溯。

**這不是正式系統，是需求訪談工具。** 目的不是「展示我們的答案有多完整」，是讓客戶在互動中容易指出「這裡不對、我們實際上是這樣做的」——所以畫面上刻意保留了大量「示範假設」標記，把還沒確認的業務規則講在明處，而不是幫客戶把決定都做完。

---

## 設計理念

### 1. 庫存總帳是唯一真相（Inventory as Cornerstone）
所有庫存數字（現有量／已保留／可用量／在途量）都從一份不可竄改的異動總帳（Ledger）推導出來，沒有任何地方直接寫死或另開一套算法。庫存管理不是七個模組裡的其中一個，是其他模組都要正確讀寫的控制中心。新功能要不要用到庫存數字，第一個問題永遠是「有沒有經過總帳」。

### 2. 訂單驅動（Pull），不是預測驅動（Push）
沒有任何東西是系統「猜」出來要買、要裁的——一切從客戶下單這個真實需求信號開始往回推。沒有安全庫存／再訂購點驅動的自動補貨（這是刻意的取捨，也是訪談要問客戶的題目：他們實際上是訂單觸發還是預測驅動？）。

### 3. 現貨 → 自製 → 採購，三層瀑布（Stock → Make → Buy）
每一筆需求的缺口，依序問：架上有沒有現貨？來不及自己裁？來不及跟供應商買？三層可以同時湊（不是三選一），對應 `planSupply()`。這是 MTO 製造業共通的 Available-to-Promise／Capable-to-Promise 邏輯，不是紙業限定。

### 4. 兩階段承諾：軟分配 → 硬分配
「產生供應建議」只計算、不寫任何資料；「確認供應方案」才真正鎖料（庫存保留）、開產令（裁切工單）、發採購單。避免系統先斬後奏。確認後庫存進入「已保留」狀態（Allocation）——帳面看得到，但已經名花有主，不能再答應給別的訂單。

### 5. 示範假設標記，誠實地把未確認的規則攤開
凡是良率、損耗、安全存量門檻、庫存過帳時點、客戶議價權限這類「demo 為了能跑先假設一個數字」的地方，畫面上都用「示範假設」小標記標出來，滑鼠移上去看假設內容。這是這個原型最重要的設計原則：**寧可讓客戶看到假設並糾正它，也不要假裝我們已經知道正確答案。**

### 6. 單一履約倉，不做跨倉自動調度
所有銷售可承諾／保留／出貨都固定以一個履約倉（八里主倉）計算，不會自動跨倉調貨。這是刻意避免「系統看得到、實際調不出來」的假承諾，代價是不會做多倉智慧調度——這個取捨要不要放寬，也是訪談題目。

## 架構取捨：為什麼是單一 HTML 檔

這份原型的價值在**流程設計跟訪談劇本**，不在這份程式碼本身。單檔、無後端、無持久化、重新整理即重置示範資料，這些選擇是為了讓訪談現場能快速迭代、隨時改、隨時給客戶看，不代表這是正式系統該有的架構。如果要往下發展成真正的系統，`Browser → JS Array → 前端計算` 這條路線要換成 `Browser → API → Application Service → Database`，含 server-side pagination／filtering／sorting——程式碼裡的表格引擎已經用註解標出這條分界線。

## 模組總覽

| 模組 | 一句話 |
|---|---|
| 總覽 | 聚合指標＋例外事件＋優先處理清單，不逐筆列原始資料 |
| 銷售管理 | 報價單 → 銷售訂單 → 供應方案（自動／手動輸入配置二選一） |
| 採購管理 | 採購單列表／驗收入庫，另有「缺料建議」彙總尚未處理的訂單缺口，可一鍵或自由手動開單 |
| 庫存管理 | 庫存狀態／總帳／捲別明細／盤點調整——唯一的數字入口 |
| 裁切管理 | 母捲裁切成品，投入／產出／剩料／損耗四段式加工流程 |
| 出貨管理 | 六段配送狀態，「已出車」這一步才真正過帳扣庫存 |
| 基礎資料 | 紙品／客戶（含專屬價格）／供應商／倉別主檔，全部可直接編輯，含刪除前的參照保護 |

## 檔案說明

- **`勝芳進銷存Demo.html`** —— 發佈到 Claude Artifact 用的原始檔，刻意不含 `<!DOCTYPE>`／`<html>`／`<head>`／`<body>`，因為 Artifact 平台發佈時會自動包一層文件骨架。
- **`勝芳進銷存Demo-本機開啟版.html`** —— 本機直接雙擊、用瀏覽器打開用，內容跟上面那份完全一樣，只是補齊了完整的 HTML 文件結構（少了它會被瀏覽器當成 Quirks Mode 解析，版面跟互動都可能跑掉）。

**兩份檔案內容必須保持同步**——修改邏輯只改 `勝芳進銷存Demo.html`，同步用一支腳本重新產生本機開啟版（把 `<style>` 結尾前的內容包成 `<head>`、其餘內容包成 `<body>`，外面加標準骨架），不要手動改兩份。

## 已知的設計缺口（訪談問題清單）

這些是原型刻意留下、還沒有答案的地方，適合直接拿去問客戶：

- 客戶「接受」報價目前完全靠業務手動判斷按鈕，系統不記錄同意方式（電話／Email／正式訂購單）、也不檢查報價是否過期
- 訂單如果中途取消，目前沒有釋放已鎖庫存保留的路徑
- 沒有安全庫存驅動的預防性採購，完全靠訂單觸發
- 裁切產能試算沒有把在途母捲算進去（跟採購的「在途」概念不一致）
- 供應商批號、裁切批次的完整追溯欄位還沒有
- 裁切工單的狀態命名（已規劃／進行中）目前是預留但沒有實際操作路徑會走到

## 若要作為其他製造業客戶的範本

可以直接沿用的骨架：三層瀑布（Stock→Make→Buy）、兩階段承諾（軟分配→硬分配）、Ledger 唯一真相、示範假設標記機制、表格引擎。

要換成客戶專屬的：品項／客戶／供應商的示範資料與命名（目前是勝芳紙業／宏泰印刷／中華紙漿等），還有各模組「示範假設」標記裡的具體業務規則假設（良率、安全存量、過帳時點等，每個產業會不一樣）。
